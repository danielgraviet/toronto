Finetuning does not need a research lab

In the next fifteen minutes we will teach a small language model to write better code for one puzzle. The trainer runs on a Daytona GPU sandbox. The graders are ordinary CPU sandboxes that execute unit tests.

Reinforcement learning is older than chatbots

Long before language models, agents learned by acting in an environment and receiving a score. Toronto has a deep streak of that research history, from games to control to the models we use today.

Coding fits the same shape. The state is the unfinished program. The action is the next token. The environment is a sandbox that runs tests and returns a reward.

Policy

David Silver: a policy is the agent's behaviour. It is a map from state to action, often a distribution over actions given a state.

In our demo the state is the text so far and each action is the next token. Click through to watch that distribution change after every sample.

Rollout

In reinforcement learning a rollout is one full trajectory of actions in an environment, from a starting state until the episode ends.

For us that means one complete code attempt. We sample token after token until the function is finished.

Reward

David Silver: a reward is a scalar feedback signal. It indicates how well the agent is doing at that step. The agent's job is to maximise cumulative reward.

Our grader turns unit test results into that scalar. Tonight it is mostly the fraction of tests that pass.

Group

A group is a set of comparable attempts scored relative to each other instead of against a single labeled answer.

In GRPO we sample several rollouts for the same prompt and reinforce the ones that beat the group mean.

Update

An update changes the policy so future behaviour prefers actions that led to higher reward.

We nudge the model weights so high scoring code becomes more likely the next time we sample.

Where Daytona sits in the stack

  • GPU sandbox Loads the model, samples completions, and runs the GRPO weight update.
  • CPU sandboxes Grade code in parallel. They never run the model. They only execute the test harness.
  • This laptop Shows the story and starts the remote job.

If you want projects that go past a thin wrapper around a hosted chat API, you need infra that can isolate untrusted code and scale the graders. Sandboxes are the boring part that makes the interesting part safe.

One use case of a wider primitive

Tonight we use Daytona sandboxes as parallel graders for GRPO. That is only one shape of the same idea. A sandbox is isolated compute you can spin up for work that should not share your laptop.

  • Cursor Cloud Agents Background coding agents can run inside Daytona sandboxes while you shut off your laptop. No more clamshelling.
  • Data and analytics jobs Run notebooks, scrapers, or batch transforms without polluting a shared machine.
  • Long running experiments Training loops, eval harnesses, and agent civilizations all need the same isolation layer.

What comes online before learning

  1. Daytona creates an ephemeral GPU sandbox for the trainer.
  2. We load a deliberately weak base policy so the starting point is honest.
  3. CPU graders warm up. Those sandboxes only run tests.
  4. A baseline eval uses the same checks we will use after training.
  5. Each tile in the grid is one rollout with a return from the grader.

Watch the policy improve on Two Sum Plus

The live run starts from an untrained policy on Two Sum Plus. Each step collects a group of answers, scores them in parallel, and updates the weights. The finale compares before and after on the same unit tests.

The model tries several answers. A grader scores them. Training nudges the policy toward the answers that scored better.

What should stick

  1. Try, grade, reinforce. You do not need an answer key for every sample.
  2. Sandboxes are safe parallel graders for coding rewards.
  3. Finetuning can be a few minutes of clear infra plus a reward you can explain in one sentence.
  4. Own the loop. Daytona is a reliable place to run the pieces that must stay isolated.
