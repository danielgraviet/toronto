# RL terminology for the Toronto demo

This guide is written to be read aloud.

> GRPO is a way of improving a model without giving it the correct answer directly. We give the model a problem, ask it to generate several different solutions, and run each solution through a test environment. The environment gives every solution a reward. GRPO then compares the solutions for the same problem and makes the better-than-average solutions more likely in the future.

A shorter version is:

> The model tries several answers, a grader scores them, and training nudges the model toward the answers that scored better.

## Reinforcement learning is bigger than language models

RL is not inherently about text. In Atari, an agent sees a screen and chooses from a small action space: left, right, up, down, fire. In AlphaGo, the agent sees a board and chooses a legal move.

The general RL idea is:

> Given the current state, a policy produces a distribution over possible actions.

For Atari, that distribution might be:

    Action:      left   right   up   down   fire
    Probability: 45%    20%     10%  15%    10%

In our demo, the state is the text written so far and the action is the next token:

    state:   "def fizzbuzz(n):\n    "
    actions: "r", "p", "return", ...

The action space is larger, but the underlying RL structure is the same.

## Machine-learning vocabulary

**Model** — A neural network that predicts the next token.

**Parameters or weights** — The learned numerical values inside the model: its enormous collection of adjustable knobs.

**Prompt** — The input given to the model, here the coding puzzle.

**Completion** — One answer generated by the model after the prompt.

**Token** — A small piece of text, such as a word, part of a word, punctuation, or a newline.

**Inference or generation** — Using the model without changing its parameters.

**Training** — Changing the parameters so future behavior improves according to an objective.

**Loss** — A number describing how undesirable the current behavior is according to that objective. We differentiate the loss to get gradients, then an optimizer applies the update.

## Classical RL terms

### Policy

A policy is a distribution of actions given a state:

    policy(action | state)

For example, policy(move left | current Atari screen) = 45%. For a language model, it is policy(next token | text generated so far). The model repeatedly chooses tokens:

    "def" → " fizz" → "buzz" → "(" → "n" → ")"

### Environment

The environment receives actions, updates the state, and returns feedback. Examples are the Atari game engine, the AlphaGo board, a robot and its sensors, or a coding agent's terminal and test suite.

In this demo, the environment happens to be a CPU Daytona sandbox. It:

1. receives a completion;
2. checks format, length, and banned patterns;
3. runs unit tests;
4. returns structured results and a reward.

The GPU sandbox generates code and trains the model. CPU sandboxes never run the model; they only grade completions.

### Reward

A numerical evaluation of an episode:

    all tests pass      → +1.0
    some tests pass     → partial reward
    tests fail          →  0.0 or negative
    banned pattern      → strong penalty
    timeout             → -1.0

The reward does not need to contain the correct code. It needs to tell us how well the attempt performed.

Designing a durable reward is often one of the hardest parts of RL. A smart model may maximize the score without achieving the real goal; this is reward hacking. If we punish length too much, it may write tiny but unreadable code. If we do not punish verbosity, it may add excessive comments. If tests are weak, it may exploit the test harness. The reward must measure the goal, not merely an easy-to-game proxy.

### Trajectory

A trajectory is the sequence of states and actions until termination:

    (state₀, action₀, state₁, action₁, state₂, ...)

In Atari:

    screen 1 → left → screen 2 → fire → screen 3 → game over

In this demo, the states are progressively longer text prefixes and the actions are generated tokens:

    prompt → generate signature → generate body → finish completion → run tests

### Episode

An episode is one complete run from an initial state until a terminal condition. The trajectory is the detailed sequence inside the run; the episode is the complete attempt as a unit.

    Atari episode:   start game → take actions → game over
    Coding episode:  receive prompt → generate completion → run tests → reward

### Rollout

A rollout is the process of letting the policy interact with the environment and collecting the resulting experience. In our one-shot task, one rollout produces one trajectory and one episode. With four generations, we perform four rollouts and collect four episodes for the same prompt.

The useful distinction is:

- trajectory = the sequence of states and actions;
- episode = one complete run;
- rollout = the act of generating and collecting that run.

### Environment step

An environment step is one action inside an interaction. In Atari, moving left once is one step. In a terminal coding agent, a step might be inspecting a file, editing a file, running tests, or reading a compiler error.

Our task is deliberately one-shot: generate code, run tests, receive reward, terminate. Terminal-bench or SWE-bench-style agents have much longer trajectories of inspection, editing, testing, and revision. They are excellent next areas to explore, but take much longer and do not fit comfortably into a 15-minute demo.

## GRPO: Group Relative Policy Optimization

GRPO generates several completions for each prompt, evaluates them, and uses their relative rewards to update the policy.

For one FizzBuzz prompt:

    Answer 1 → reward 1.0
    Answer 2 → reward 0.0
    Answer 3 → reward 0.5
    Answer 4 → reward 1.0

The two 1.0 answers are better than this group's average. The 0.0 answer is worse. GRPO increases the probability of tokens from better-than-average answers and decreases the probability of tokens from worse-than-average answers.

### Groups must be comparable

Each group contains multiple answers to one prompt. We do not directly compare unrelated problems.

Valid group:

    Prompt: Write a function that solves Two Sum.
    Four answers to that same prompt → four comparable rewards

Not one meaningful group:

    Two Sum answer → reward 1.0
    FizzBuzz answer → reward 1.0
    JSON parser    → reward 1.0
    Linked list    → reward 1.0

A 1.0 on Two Sum does not prove it is better than a 1.0 on FizzBuzz. We can process different prompts in one batch, but each prompt has its own group and its own within-prompt baseline.

### Relative advantage

Advantage means how much better or worse a completion was than its group's other attempts. A simplified version is:

    advantage = reward - average reward in this group

Real implementations commonly normalize rewards within groups. The key idea is that reward is interpreted relative to comparable attempts.

### How can RL learn without a correct answer?

Supervised fine-tuning receives a target:

    prompt → known correct completion

GRPO samples its own answers:

    model → completion → tests → reward

A simplified policy-gradient expression is:

    loss ≈ - advantage × log probability of the sampled completion

Positive advantage makes the sampled behavior more likely; negative advantage makes it less likely. It may resemble SFT because successful behavior becomes more likely, but the teaching signal is different: SFT imitates a provided answer, while RL learns from consequences produced by an environment. Our test suite is the source of those consequences.

### KL penalty

A KL penalty discourages the trained policy from drifting too far from the original model. It lets us learn the task without destroying broader behavior.

## Batch size, group size, and model steps

### Group size

Group size is the number of completions generated for one prompt:

    group size = 4
    one prompt → four attempts

Libraries often call this num_generations.

### Batch size

Batch size is the number of prompts whose groups contribute to one collected training batch:

    batch size = 8 prompts
    group size = 4 completions per prompt

This produces 8 × 4 = 32 completions. We do not update after each prompt. We grade all 32, perform eight separate within-prompt comparisons, aggregate the training signal, and make one optimizer update.

The student analogy:

- Batch size 1: solve one math problem and study one mistake. Granular, but slow and sensitive to one example.
- Batch size 10: identify patterns across mistakes—bad algebra, rounding, forgotten conversions, or missing formulas—and study those general patterns.

A larger batch can stabilize the update, but costs memory, generation time, sandbox evaluations, and delay before feedback. That is why a stage demo uses a small batch.

### Why not use 10 or 20 generations?

A group of 16 gives more samples and may make the comparison more statistically stable, but it costs four times as much as a group of 4:

    1 prompt × 4 generations  = 4 evaluations
    1 prompt × 16 generations = 16 evaluations

There are diminishing returns. If the weak model produces mostly failures, more failures may not create useful signal. Four is a practical stage compromise.

### One training step

For this demo, one training step is one complete collect-and-update cycle:

1. Select the prompt batch.
2. Generate the configured completions.
3. Grade them in CPU sandboxes.
4. Convert results into rewards.
5. Compute within-group advantages.
6. Calculate the GRPO loss.
7. Backpropagate to calculate gradients.
8. Have Adam apply one parameter update.
9. Save metrics and display results.

With one live prompt and group size four, one step is exactly:

    1 prompt → 4 completions → 4 sandbox evaluations
    → one four-answer comparison → one GRPO loss
    → one Adam parameter update

With eight prompts, one step is:

    8 prompts → 32 completions → 32 evaluations
    → 8 separate comparisons → one aggregated update

Some trainer configurations add gradient accumulation or multiple optimization iterations. For this demo, we configure one collected batch followed by one optimizer update as one model step.

### Why six steps?

Six is a visible training budget chosen for the stage. It is not derived from eight prompts or four generations. The dataset can be sampled again on each step.

With one prompt, group size four, and six steps:

    6 model steps × 4 completions = 24 completions and evaluations

With eight prompts:

    6 model steps × 8 prompts × 4 completions = 192 completions and evaluations

“Six steps” means six parameter updates, not six prompts or six tests.

## Learning rate and optimizer

The learning rate controls how large each parameter update is. Imagine a character walking across a field:

- long legs cover lots of ground but make precise placement difficult;
- short legs make precise adjustments but take many steps to travel far.

A high learning rate moves quickly but can overshoot. A low learning rate is precise but may learn slowly.

Adam is the optimizer that applies the gradient update. Imagine a person named Adam standing behind the model. Adam watches the direction and recent history of each suggested adjustment. If a direction has been consistently useful, he moves more confidently; if the signal is noisy, he makes a more measured move. That is not the exact algorithm, but it is a memorable picture of Adam adapting individual updates.

Muon is another optimizer with a different rule, particularly suited to matrix-shaped neural-network parameters. Both answer: given the gradient, how should the update be applied?

## Checkpoints and Daytona

A checkpoint is a saved copy of model parameters at a point in training:

    model before training → GRPO steps → model after training

This lets us compare before and after and recover from a failed run. Daytona gives us a reproducible GPU sandbox for the trainer and a known snapshot for the installed software and GPU environment. We still explicitly export weights to durable storage before deleting the sandbox; a snapshot is not a substitute for a durable model artifact.

## Stage configuration

For the clearest live explanation:

    batch size      = 1 prompt
    group size      = 4 completions per prompt
    sandbox pool    = 4 or more CPU sandboxes
    max completion  = 192 tokens
    training steps  = 6

One step is four completions, four evaluations, one within-prompt comparison, one GRPO loss, and one Adam update. After six steps, there are six model updates and 24 completions.

For a larger rehearsal:

    batch size      = 8 prompts
    group size      = 4 completions per prompt
    sandbox pool    = 32 CPU sandboxes
    max completion  = 192 tokens
    training steps  = 6

One step processes 32 completions, compares eight separate groups, and makes one aggregated update. Six steps processes up to 192 completions. The CPU pool is only a parallelism setting: it controls how many grading jobs run at once.

## Final summary

> Batch size tells us how many prompts contribute to one update. Group size tells us how many attempts we make for each prompt so GRPO can compare them. An environment step is one action inside an interaction, while a training step is the complete process of collecting rewards and updating the model.

> The model is learning from consequences. It generates code, the sandbox tests that code, and GRPO uses the relative test results to adjust the model's policy—even though nobody gave it the correct solution token by token.
